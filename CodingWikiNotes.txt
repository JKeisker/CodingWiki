SECTIONS I & II: INTRO & MIGRATIONS
--------------------------------------------------------------------------------------------------------------------
1) Create solution w/ 3 projects (.Net7):
	a) DataAccess
		-Packages: Microsoft.EntityFrameworkCore.SqlServer(7.0.20)
			   Microsoft.EntityFrameworkCore.Tools(7.0.20)
		-Projects: Models
	b) Models
		-Packages: Microsoft.AspNetCore.Mvc.ViewFeatures(2.3.9)
	c) Web
		-Packages: Microsoft.EntityFrameworkCore.Design(7.0.20)
			   Microsoft.EntityFrameworkCore.Proxies(7.0.20)
			   Microsoft.VisualStudio.Web.CodeGeneration.Design(7.0.12)
		-Projects: Models, DataAccess


2) Create ApplicationDbContext.cs in DataAccess project
	In ApplicationDbContext 
		a) create DbSet<modelname> for each model that should be a Table in the DB.
		b) use [Key] data annotation for primary key of table
		b) add db connection reference in method 'OnConfiguring(...)

3) Add Migration
	a) set DataAccess project as startup project
	b) set PMC's to same project as 'a)' = DataAccess startup project
	c) Make desired changes to Model project
	d) If new table, add as DbSet to ApplicationDbContext
	e) PMC: add-migration AddBookToDB
	f) PMC: update-database

4) Remove Migration (***If you run this AFTER update-database for the migration you want to remove,
			it will screw up your code)
	a) ***Important: only use remove-migration when you are unhappy w/ a migration 
			AND have not pushed it to the DB.
	b) To remove last migration => remove-migration
		Now the unwanted migration will removed, and ApplicationDbContextModelSnapshot.cs will have been 
		updated to previous value/state. ***HOWEVER, in your model, it will still be set to the changes you were
		trying to set w/ the migration you just removed!!!
	

***5) IF you do run a migration and update-database w/o for example creating a DbSet in ApplicationDbContext,
	then you must follow these steps:
	a) Revert DB (roll back to prev state): Update-Database <PreviousMigrationName>
		***<PreviousMigrationName> : use class name w/o the date/timestamp prefix
	b) Run : remove-migration

6) NOTE: NEVER arbitrarily remove a migration unless you know what you're doing!
	ONLY make changes in the models and ApplicationDbContext!!

7) Rolling back to old migrations (ONLY applies to EF Core..AND NEVER DO THIS IN PRODUCTION THE TABLES WILL BE GONE!!!!)
	a) update-database NameOfMigrationWeWantToGoBackTo
	b) To return to previous state, just run 'update-database' and all reversions will be undone.
	
8) ***Most conservative/safe thing is to just add migrations rather than removing or rolling back. Pretty much
	every issue can be fixed by simply creating new migrations rather than using other methods.

9) More commands: 
	a) get-migration
	b) drop-database
	c) update-database - after running drop-database, this cmd will bring it back

10) Data Seeding
	Use ApplicationDbContext => OnModelCreating(ModelBuilder modelBuilder)		
				    {
					modelBuilder.Entity<Book>.Property(u=>u.Price).HasPrecision(10,5);
					modelBuilder.Entity<Book>.HasData(
						new Book { BookId = 1, Title = "SpiderMan", ISBN = "123B12", Price = 10.99m }
				    };

SECTION III: DATA ANNOTATIONS

Chp 30: EF Core Power Tools

Do not check dab-options.json into source control if it contains sensitive connection strings, as this risks leaking credentials.  However, the configuration file dab-config.json (which stores the Data API Builder configuration) should generally be stored in source control for reproducibility, while the generated dab-build.cmd file is part of the scaffolding process. 

Here are the specific guidelines for these files:

dab-config.json: This file stores the Data API Builder configuration and is intended to be stored in source control.  It allows the API definition to be versioned and shared among developers.
dab-build.cmd: This file is generated by EF Core Power Tools to install the DAB CLI and build the configuration. It is a build script that can be checked in, but note that the tool aims to avoid hand-editing this file so it can be regenerated if the source schema changes. 
Security Warning: If your project generates an .env file containing connection strings (e.g., dab-connection-string=...), you must exclude this file from source control.  Add the following line to your .gitignore file:
.env

SECTION V: FLUENT API

Definition - Fluent API is another way to configure the domain classes aside from 'Data Annotations'.
To use Fluent API, you need to do that in the ApplicationDbContext method 'OnModelCreating(ModelBuilder modelBuilder)' override.
Classes copied under 'FluentModels' folder to demo fluent api.

If both Fluent API and Data Annotations are used, if there is any contradiction Fluent API will be used.
